# Dragon Drop

A map editor that a human and Claude work in together (formerly "AI Mapmaker"; the repo, package names and the `mapmaker` MCP server key keep the old name). Read `docs/PLAN.md` for the roadmap and `docs/SETUP-WINDOWS.md` for setup.

## If this session is for making maps (e.g. Remote Control from the DM's phone)

- Use the **mapmaker** MCP tools (from `.mcp.json`). They act on the project open in the editor. The app must be running (`pnpm start`). If the tools are missing, say so; don't try to edit map files by hand.
- The tools' own instructions (sent by the MCP server) explain coordinates, units and workflow. In short:
  - Look with `render_preview` before and after edits.
  - Call `get_changes_since` at the start of each turn to see the DM's hand edits.
  - Prefer `add_landmass` / `add_mountain_range` over many small `sculpt` calls, then `erode` to weather new ranges.
  - Use `save_checkpoint` before big experiments. `compare_to_reference` checks the map against a sketch.
  - Never call `generate_terrain` on an existing map unless asked.
  - Battlemaps are separate projects (`create_battlemap`, then `render_battlemap`, `add_room`, `paint_floor`, `add_wall`, `add_door`, `add_light`, `export_battlemap`), in grid squares. World-map tools refuse on them and the reverse.
  - Rivers are worked out from the terrain and rainfall, never drawn by hand. To make one bigger or start one (a great spring, a waterfall), use `add_river_source`; `check_hydrology` explains the water (lakes with no way out, rivers through dry land); `list_river_sources` shows what each source feeds.
  - The DM can select a point, an area (rectangle, circle, freehand) or a feature in the editor. When they say "this", "here" or "the selected ...", call `get_selection` first (`render_preview` with `selection: true` looks at it; its outline is gold on every preview). While they have locked your edits to an area, terrain changes are clipped to it and feature edits outside it are refused: say so and let them unlock; never work around it. You can't change or clear a locked selection; with no lock, `select_area` / `clear_selection` highlight an area for them.
  - The painted map has many kinds of ground (tundra, steppe, savanna, marsh, badlands, glacier, forests and more: the editor's Ground legend). `list_grounds` lists them with where each appears and how to get it (climate-region temperature and moisture, height); `get_selection` reports which are in an area. Ground is paint, not lore.
  - Named places and labels (`add_place`, `add_label`) are canon too: only use names the DM gave or confirmed. A place's `type` picks its marker from a set of about 40 (castle, temple, cave, lighthouse, peak... as small pictures): choose the one that fits what the place is.
  - The DM may be watching the read-only phone page (`/view`), which updates live as you edit.
- **Lore is the DM's.** `projects/<id>/brief.md` records established facts, measured facts and open questions. Never invent canon for a setting (names, history, who lives where). Propose, mark it as a proposal, and record it only when the DM confirms.
- Each map's lore lives in its own `projects/<id>/brief.md` on the DM's machine (the `projects/` folder is gitignored: no map or brief is ever committed, because the maps are the DM's own work). Read it with `get_brief` before you touch a setting; the scale, winds, reefs, named places and climate-region recipes the DM confirmed are recorded there, and only there.

## If this session is for developing the app

- pnpm monorepo, TypeScript, Node 22+. No build step for the server (run through `tsx`); the editor builds with Vite.
  - `packages/core`: heightmap document (battlemaps reuse it: `battle.ts` holds floors as material ids, procedural floor textures, wall/light helpers and the Universal VTT / Foundry exporters), terrain ops, features (places, labels), `MapSession` (all edits go through `execute()` for shared undo and authorship), hydrology and erosion, climate (`computeDerived`), renderers (`renderInto` relief, `renderPainted` Painted Relief with tile redraws), WS protocol. Pure TS, browser- and Node-safe.
  - `packages/tools`: every Claude tool, defined once with zod. Used by both the chat agent and MCP. `MAPMAKER_INSTRUCTIONS` is the shared system prompt.
  - `apps/server`: project store, hub (state + WS sync), MCP endpoint, chat agent (Claude API streaming tool loop).
  - `apps/desktop`: the Windows app (Electron). Not part of the pnpm workspace; it has its own `npm install`. `scripts/prepare.mjs` bundles the server with esbuild (nothing from `projects/` ships: the maps there are the DM's own, so a new install starts with the generated "First Map" that `Hub.ensureProject` makes; a test fails if a sample is bundled again), `main.cjs` starts it as a child process (via `ELECTRON_RUN_AS_NODE`) and shows the editor, `electron . --smoke-test` checks it end to end. GitHub Actions (`.github/workflows/desktop.yml`) builds the NSIS installer on Windows and smoke-tests the installed app. Settings (API key, maps folder) live in the user's app-data folder, not `.env`.
  - `apps/editor`: React UI, canvas map view, chat panel, inspector and climate panel (`Panels.tsx`), label drawing with Cinzel (`drawFeatures.ts`; names and markers are sized by `textScale`: they follow the map's scale when zooming out but grow only slowly, to at most 1.8 times, when zoomed in, times the sidebar's Label size setting), and the phone viewer at `/view` (`Viewer.tsx`).
- Claude Code first-run setup: Claude Code isn't bundled and every user signs in themselves. The panel shows `ClaudeInstallSteps` (`ClaudeButton.tsx`) with an install button; `main.cjs` `startInstall` runs Anthropic's official installer (command fixed in `installCommand`, never taken from the page) visibly in the pty and reports `dd:claude-installed`; `claudeCheck` gives installed/version for Settings. The smoke test swaps in a harmless stand-in under `SMOKE`. The terminal panel runs `settings.terminalCommand`: empty means Claude Code with `--mcp-config` and the Assist hooks, anything else runs through the shell in the Claude workspace (which also holds `AGENTS.md` and `GEMINI.md`, harmless next to `CLAUDE.md`: Claude Code reads only `CLAUDE.md` when both exist). Which assistant a start command runs is worked out from the command (`profileFor` in `apps/desktop/assistants.cjs`: claude, codex, gemini, antigravity or opencode, also through `ollama launch <x>`; empty is the default, anything else is unknown), and `syncAssistantConfigs` writes that assistant's own project file in the workspace so the map tools are connected with no copying: `.mcp.json` (Claude Code started by another program, plus the `enabledMcpjsonServers` pre-approval in `.claude/settings.json`), `.codex/config.toml` (a marked block; Codex only reads it once the folder is trusted), `.gemini/settings.json`, `opencode.json`, `.agents/mcp_config.json`. Our entry is taken out of every other assistant's file (recognised by its 127.0.0.1 `/mcp` address), what else the person put in those files stays, and an invalid file is left alone; the default Claude Code gets the map tools from `--mcp-config` alone, so a second definition can't ask for approval. Settings shows whether the chosen assistant is connected automatically (`describe`). Adding an assistant: its entry in `JSON_TARGETS` (or a writer like `syncCodex`), a name in `BY_PROGRAM`, tests like `apps/desktop/test/assistants.test.mjs`, a row in `docs/SETUP-WINDOWS.md` §6b, and a check against the real tool (its own "list MCP servers" command, with the key only in the environment). The Settings preset dropdown fills the command.
- Water (`hydrology.ts`, `hydroSummary.ts`): rivers come from flow accumulation weighted by runoff (`runoffOf(temp, moist)`, so rain decides where rivers start and how big they are), the threshold is a share of the map's total runoff, a lake's outflow is a river head, and `RiverSource`s (`features.sources`, sizes in `RIVER_SIZE_SHARE`) inject extra flow at a point or at a place. `resolveRiverSources` turns them into `inflows` for `computeDerived` (the hub recomputes when they or their place move). `Derived.hydro` is the account that `check_hydrology` reads. Stages 2-4 (opt-in valley carving, river/lake objects, meanders and deltas) are in `docs/PLAN.md`.
- Selection (`packages/core/src/selection.ts`): `Selection` is a point, an area (rect/circle/polygon) or a feature id; the editor sends it (`{t:"selection"}`, with `lock`, and `{t:"view"}` for what is on screen), the hub keeps it per open map (reset on open; a deleted feature deselects) and echoes it, and Claude reads it with `get_selection` (`selectionReport`). The lock is `MapSession.editLock` (set by the hub from an area or a climate region): in `execute()` it applies to author `claude` only, clips height changes with a feathered mask (nothing outside the shape changes, the undo rect shrinks to the shape), and throws `LockedEditError` for feature edits outside the shape and for sea level, climate settings and checkpoint restores. The editor's side is the Select area tool in `MapView.tsx` (rectangle, circle and freehand are drags; polygon is corner by corner with `polyDraft`, closed by double-click, Enter or a click on the first corner), `SelectionBar.tsx` (lock checkbox, "Ask Claude about this" box that types one line into the terminal through `useAssist().ask` only when Claude Code is idle, `askMessage` in `assist.ts`), and `store.setSelection`.
- Rivers in the painted style are painted into the map by `renderPainted` (`riverPaint.ts`), not drawn over it: `rasterRivers` gives each pixel near a river its distance to the water's edge, the river's size and how steeply it drops (m per km); the painter then shades the water from the ground (calm dark water on the flats, rapids and falls where it drops, canopy hiding narrow rivers in jungle, brackish at the mouth), paints banks that follow the land (floodplain, gravel, oasis ribbon, mud), and the shading sees a valley cut into the ground (`valleyDepth`). The paint worker gets the rivers with every climate frame, `derivedChange` counts a changed river as a change, and the Rivers layer switch is `PaintView.rivers`. The vector overlay in `MapView` (and the export's rivers option, and previews from the server) are for the Relief style only. In `hydrology.ts` a river's meander follows its slope (straight when steep, wandering on the flat) and dies away at junctions so tributaries meet exactly.
- Biomes in the painted style (`biomeLook.ts`): land that is neither jungle nor desert gets the ground its climate makes, from `biomeWeights(t, m, e, rugged)`: tundra, boreal conifer, temperate mixed forest, warm broadleaf forest (the temperature bands add up to one and fade into each other; above the treeline, about 700 m, the forest's share becomes alpine meadow), steppe or savanna where it is drier, marsh on low flat wet ground and along big rivers (the painter passes the river raster's closeness to `biomeWeights` as `nearWater`). A wet archipelago has moisture near 1 almost everywhere, so the variety comes mostly from temperature (latitude and height). `paintBiomes` mixes each biome's texture (from the canopy, clump, hue, rock and fine noise) over the palette colour, scaled by `(1 - jungle) * (1 - desert)`; tall forests also hide gentle low rock. On top of the biomes lies more ground in particular places (`Ground` in `biomeLook.ts`): beach on low gentle coast, mangrove on warm wet coast (further in along a river), reeds and lake-shore wetland (`lakeShoreDistance` gives the distance to a lake), glacier on the highest coldest snowy ground (painted after the snow), heather moor and peat bog on cool wet uplands, Mediterranean scrub (chaparral) where it is warm and not quite dry, badlands where dry ground is rugged, salt flats on very dry low flats, stony desert (the desert's version where the ground is rugged), and the wet forests: cool temperate rainforest on a wet coast below the treeline, cloud forest on warm wet mountainsides, bamboo stands and autumn colour in the cooler mixed woods (the last three are patchy: the painter breaks them up with noise). `get_selection` reports the shares of each kind of ground in an area (`biomes`, including jungle and desert) and the most common as `climate.biome`.
- Volcanic ground is a climate-region setting like bare stone: `ClimateRegion.volcanic` (0..1) gives a `Derived.volcanic` plane (`regionVolcanic`), which travels after the stone plane on the wire (`packDerived`: the stone plane is zero-filled when only volcanic is there), counts in `derivedChange`, and is painted by `renderPainted` as pale ash plains with cinder-brown patches and near-black basalt fields. Lava flows (`lava.ts`) are worked out like rivers but with a lava's physics, from the heights and the volcanic plane only (so every tile agrees; `lavaOf` caches them per `Derived`): vents at the summits and upper flanks of volcanic ground; each flow has a heat budget that every step spends (cheap on steep flanks, dear on flat ground where lava stalls); depression filling like the rivers (`computeFlow` on the volcanic part of the map: a flow fills a small hollow and spills over, but a basin deeper than 90 m holds it); forks that don't merge; narrow at the vent and broad lobes with a blunt front; meander; it ends where the volcanic ground ends or at the sea. About a third of flows are fresh and glow (scorched edge, dark crust over an orange body, bright core, self-lit and painted after the shading and the rivers, which they bury); the rest are cooled black basalt with ropy streaks. `rasterLava` gives each pixel its distance to the nearest flow. River banks leave volcanic ground alone, like stone. Claude sets it with `volcanic` on `add_climate_region` / `update_climate_region`, only where the DM said the land is volcanic; the editor's region panel has a "Volcanic ground" tick.
- Place kinds (`packages/core/src/placeKinds.ts`) are the one list of what a place can be (`PLACE_KINDS`: id, name, group, label size, name-placement rank, hint, and `picture`): `PlaceType`, `PLACE_SIZE`, the zod enum of `add_place` / `update_place`, the editor's picker (`PlaceKindPicker.tsx`, grouped, in the Place tool and the inspector) and the name-placement order all derive from it. The first nine kinds are the original abstract symbols (drawn by `marker()` in `drawFeatures.ts`, kept as they were so old maps look the same); every other kind is a small vector picture in `placeIcons.ts` (shapes in a -1..1 box: ink with a white outline, some white cut-outs and tints; written against a tiny `IconCtx` so it also runs in tests). `drawPlaceMarker` draws either kind. Adding a kind: add it to `PLACE_KINDS` and, if `picture` is true, to `PLACE_ICONS` (a test fails until both agree). Unknown kinds from a newer file read as "other" (`placeKind`). The server's raster previews still draw a plain dot for every marker.
- `GROUND_INFO` in `biomeLook.ts` is the one list of every kind of ground (id, name, group, swatch colour, where it appears, `recipe` = how to get it); it also feeds the `list_grounds` tool and the "Ground types" section of `MAPMAKER_INSTRUCTIONS`, so Claude Code in the terminal knows the grounds (a new ground needs its recipe, and the instructions' list updated); the editor's "Ground legend" panel (`GroundLegend` in `Panels.tsx`, painted style only) shows it, and a test keeps it in step with the biomes, the extra grounds and the region-set ones.
- Keep the server's main thread free: never use the synchronous gzip/gunzip (a 2048 map is 17 MB and froze it for about 500 ms per save), take any snapshot of the map before the first `await`, and keep heavy maths in the compute workers. In the editor, a full-map repaint is expensive (about 1.5 s of main thread): derived layers repaint only the box that changed (`derivedChange`), and the load placeholder is `renderPlaceholder`.
- Painting runs in a worker, never on the main thread: `PaintEngine` (core) holds heights, climate layers and noise and makes tiles and sliced full repaints (blurs computed once, `paintPrep`); `paintWorker.ts` / `paintClient.ts` wrap it; the map view only draws the pixels it is sent. Don't hold or upload big buffers on the main thread (an 80 MB `fetch` body blocked it for seconds): fetch and upload in workers. The texture noise is cached on disk (`noiseFile.ts`, `NoiseStore`, `/api/noise`): if you change what `noise.ts` or `noisecache.ts` produce, bump `NOISE_CACHE_VERSION` (a fingerprint test fails until you do).
- Assist mode: `packages/core/src/assist.ts` (pure rules and the typed message, tested), `POST /api/claude-hook` in `apps/server/src/http.ts` (Claude Code's hooks report idle/busy/blocked; the answer must stay empty because hook output can reach Claude), the desktop app writes the hooks into its Claude workspace `.claude/settings.json` (`withDragonDropHooks` in `main.cjs`, keeps the DM's own settings) and `dd:term-status`, the editor side is `useAssist.ts` and `assistBus.ts`. The desktop app also posts a SessionEnd to `/api/claude-hook` whenever any terminal program ends, so a stale idle state can't outlive Claude and Assist never types into another program. Never type into the terminal unless the hooks say Claude is idle: an Enter at a permission prompt would answer it. Typed text must be one line with no control characters (`oneLine`).
- Phone access goes through Tailscale (`tailscale serve`) with `MAPMAKER_ALLOWED_HOSTS`; the server itself stays on localhost.
- Commands: `pnpm test` (vitest), `pnpm typecheck`, `pnpm build`, `pnpm e2e` (Playwright smoke test using the scripted model), `pnpm dev`.
- `MAPMAKER_FAKE_MODEL=1` swaps Claude for a scripted model, for UI work without API spend.
- Keep the server bound to localhost and keep the Host/Origin checks in `apps/server/src/http.ts`. The chat spends the user's API credit.
- Access key (`Config.accessToken`, env `MAPMAKER_ACCESS_TOKEN`, 16+ characters or the server won't start): when set, every `/api/*`, `/mcp` and `/ws` request must carry it, as `Authorization: Bearer <key>` (Claude Code's map tools, its hooks, tests) or as the `dd_session` cookie (HttpOnly, SameSite=Strict) that opening any page with `?t=<key>` sets before redirecting to the same address without it (`authorised`, `sameSecret` in `http.ts`; compared in constant time; the static editor files stay open and the Host/Origin check still comes first). The desktop app always sets one: made once per install into the settings file (`loadSettings`), passed to the server, put in the window's first address (`editorUrl`), in the map tools file Claude Code is handed with `--mcp-config` (`mcpConfigFile()`) and in the header file the Claude hooks read with curl's `-H @file` (`hookHeaderFile()`), both in the app-data folder, and in the terminal's environment as `DRAGON_DROP_KEY` (the assistants' project files only name that variable; Antigravity's file holds the key because it can't read the environment). No file in the Documents workspace may hold the key, because Documents is often synced to the cloud: a unit test and the smoke test scan the workspace for it. The smoke test asserts a request without the key gets 401. The developer setup stays open unless the variable is set; `pnpm e2e` runs with one. A new route under `/api` is protected automatically; a new way to reach the server needs the same check.
- The editor page is served with a Content-Security-Policy (`editorCsp` in `http.ts`; `pnpm e2e` fails on any violation, so a new external script, font or connection has to be allowed there on purpose). The Electron window is sandboxed, can't leave `http://localhost:<port>/`, opens no pop-ups, refuses browser permission requests, and every `dd:*` IPC handler checks `fromEditor`. `--smoke-test` asserts the sandbox and the headers; keep it that way when adding bridge functions. `apps/desktop` writes only inside the user's Documents\Dragon Drop\Claude workspace and the app-data folder.
- Controls follow the conventions of other map programs (`docs/CONTROLS.md` compares them; keep it true when you change a key). Tool keys live in one list per kind of map (`toolDefs.ts` for world maps, `BATTLE_TOOL_GROUPS` in `Battle.tsx`) that the toolbar, `App`'s key handler and the `?` sheet (`ShortcutHelp.tsx`) all read. View keys (`+ - 0`, arrows) are pure rules in core's `viewKeys.ts`, applied by both `MapView` and `Battle`; they and the tool keys must stay out of text boxes and the terminal (`isTyping`, and Ctrl+S skips `.xterm`). `Ctrl+S` sends `save_now`; the hub saves, and answers `saved` only if the map really is on disk. A new key needs a row in the sheet and in CONTROLS.md.
- Map files are versioned (`packages/core/src/format.ts`, `formatVersion` in `project.json`; a missing one means 1). If you change what a saved map contains or means (a field renamed, a unit changed, a layer stored differently), raise `CURRENT_FORMAT` and add the step to `MIGRATIONS`, with a test; adding an optional field old files simply lack needs no new version. `ProjectStore.load` refuses a newer map (`NewerFormatError`, files untouched), copies an older one to `backups/` before migrating it, and sets an unreadable `features.json` aside instead of overwriting it (`takeNotices` hands the hub what to tell the person). Rolling backups are checkpoints with `auto: true` (`Hub.maybeAutoBackup` after a save, `HubOptions.autoBackupMs` / `autoBackupKeep`, `MAPMAKER_AUTO_BACKUP_MINUTES` / `_KEEP`; `pruneAutoCheckpoints` never deletes a person's own). Checkpoint writes for one map run one after the other (`serial`), and a checkpoint snapshots the map before its first `await`. `docs/MAP-FILES.md` describes the files for users.
- Asset library (`apps/server/src/assets.ts` and `zip.ts`; `packages/core/src/assets.ts`, `pck.ts`, `imageSize.ts`): the folder set in Settings (`MAPMAKER_ASSETS_DIR`) can hold any mix of folders of pictures (each folder directly inside it is a pack, and a folder called Floors, Props, Doors... gives the kind: `categoryOf`), `.zip` files (`readZipIndex`: stored and deflated, zip64, inflate limited to the declared size, unsafe paths dropped) and pack files made by other map tools (Godot PCK archives: found by a name ending `_pack` or `.pck`, then checked by the `GDPC` signature). Everything is read in place and never copied. Pictures are PNG, JPEG or WebP: `decodeImage` draws PNG and JPEG, so WebP shows in the editor but server renders and exports skip it (counted as missing) until a decoder is added. A pack's own info file (`packs/<id>.json` or `pack.json`) may say `allow_3rd_party_mapping_software: false`: that pack is listed but never served or drawn, and that must stay. Don't name other mapping programs or their file formats in code, UI text, docs or tests (say "asset packs"); test fixtures use made-up extensions such as `.example_pack`. Objects are 256 px per grid square at scale 1.
- File types (`packages/core/src/formats.ts`, `docs/FORMATS.md`): the one list of what Dragon Drop reads and writes, with what does not work. The chat's file picker (`REFERENCE_PICTURE_ACCEPT`), the reference listing, the asset library's picture, zip and pack-file rules and the battlemap export formats (`BATTLE_EXPORT_FORMATS`: the export tool, the download route and `Hub.battleExport`) all take their lists from it, and `docs/FORMATS.md` is made from it with `pnpm formats`; a test fails if the page and the list differ or if a claim stops being true (what decodes, what the library lists, what exports). When you add or drop a format, change the list, run `pnpm formats` and keep the Limits column honest.
- The whole `projects/` folder is gitignored (the DM's maps, briefs and chats are private and never committed). A new install makes a generated "First Map" (`Hub.ensureProject`); tests and the e2e build their own maps from generators and synthetic shapes, never from a real campaign world.
