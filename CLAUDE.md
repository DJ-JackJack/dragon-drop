# Dragon Drop

A map editor that a human and Claude work in together (formerly "AI Mapmaker"; the repo, package names and the `mapmaker` MCP server key keep the old name). Read `docs/PLAN.md` for the roadmap and `docs/SETUP-WINDOWS.md` for setup. **`docs/CHECKLIST.md` is the working list the person and Claude go through:** tick an item there (with the date) when it is done, and add new ones where they belong.

## If this session is for making maps (e.g. Remote Control from the DM's phone)

- Use the **mapmaker** MCP tools (from `.mcp.json`). They act on the project open in the editor. The app must be running (`pnpm start`). If the tools are missing, say so; don't try to edit map files by hand.
- The tools' own instructions (sent by the MCP server) explain coordinates, units and workflow. In short:
  - Look with `render_preview` before and after edits.
  - Call `get_changes_since` at the start of each turn to see the DM's hand edits.
  - Prefer `add_landmass` / `add_mountain_range` over many small `sculpt` calls, then `erode` to weather new ranges.
  - Use `save_checkpoint` before big experiments. `compare_to_reference` checks the map against a sketch.
  - Never call `generate_terrain` on an existing map unless asked.
  - Battlemaps are separate projects (`create_battlemap`, then `render_battlemap`, `add_room`, `paint_floor`, `add_wall`, `add_door`, `add_light`, `export_battlemap`), in grid squares. World-map tools refuse on them and the reverse.
  - Rivers are worked out from the terrain and rainfall, never drawn as lines. To make one bigger or start one (a great spring, a waterfall), use `add_river_source`; to make one run along a course the DM wants, `draw_river` (it cuts a channel the water then follows, and a source at its top); `check_hydrology` explains the water (lakes with no way out, rivers through dry land); `list_river_sources` shows what each source feeds.
  - The DM can select a point, an area (rectangle, circle, freehand) or a feature in the editor. When they say "this", "here" or "the selected ...", call `get_selection` first (`render_preview` with `selection: true` looks at it; its outline is gold on every preview). While they have locked your edits to an area, terrain changes are clipped to it and feature edits outside it are refused: say so and let them unlock; never work around it. You can't change or clear a locked selection; with no lock, `select_area` / `clear_selection` highlight an area for them.
  - The painted map has many kinds of ground (tundra, steppe, savanna, marsh, badlands, glacier, forests and more: the editor's Ground legend). `list_grounds` lists them with where each appears and how to get it (climate-region temperature and moisture, height); `get_selection` reports which are in an area. Ground is paint, not lore.
  - Named places and labels (`add_place`, `add_label`) are canon too: only use names the DM gave or confirmed. A place's `type` picks its marker from a set of about 70 (castle, temple, cave, lighthouse, peak, and 30 shops and trades from a blacksmith to a gambling den, as small pictures): choose the one that fits what the place is.
- **Lore is the DM's.** `projects/<id>/brief.md` records established facts, measured facts and open questions. Never invent canon for a setting (names, history, who lives where). Propose, mark it as a proposal, and record it only when the DM confirms.
- Each map's lore lives in its own `projects/<id>/brief.md` on the DM's machine (the `projects/` folder is gitignored: no map or brief is ever committed, because the maps are the DM's own work). Read it with `get_brief` before you touch a setting; the scale, winds, reefs, named places and climate-region recipes the DM confirmed are recorded there, and only there.

## If this session is for developing the app

- pnpm monorepo, TypeScript, Node 22+. No build step for the server (run through `tsx`); the editor builds with Vite.
  - `packages/core`: heightmap document (battlemaps reuse it: `battle.ts` holds floors as material ids, procedural floor textures, wall/light helpers and the Universal VTT / Foundry exporters), terrain ops, features (places, labels), `MapSession` (all edits go through `execute()` for shared undo and authorship), hydrology and erosion, climate (`computeDerived`), renderers (`renderInto` relief, `renderPainted` Painted Relief with tile redraws), WS protocol. Pure TS, browser- and Node-safe.
  - `packages/tools`: every Claude tool, defined once with zod. Used by both the chat agent and MCP. `MAPMAKER_INSTRUCTIONS` is the shared system prompt.
  - `apps/server`: project store, hub (state + WS sync), MCP endpoint, chat agent (Claude API streaming tool loop).
  - `apps/desktop`: the Windows app (Electron). Not part of the pnpm workspace; it has its own `npm install`. `scripts/prepare.mjs` bundles the server with esbuild (nothing from `projects/` ships: the maps there are the DM's own, so a new install starts with the generated "First Map" that `Hub.ensureProject` makes; a test fails if a sample is bundled again), `main.cjs` starts it as an Electron utility process (`utilityProcess.fork`, told to start by `MAPMAKER_START` and to stop through its parent port; the `RunAsNode` fuse is off, so the exe can't be run as Node) and shows the editor, `electron . --smoke-test` checks it end to end. GitHub Actions (`.github/workflows/desktop.yml`) builds the NSIS installer on Windows and smoke-tests the installed app. Settings (API key, maps folder) live in the user's app-data folder, not `.env`.
  - `apps/editor`: React UI, canvas map view, chat panel, inspector and climate panel (`Panels.tsx`), label drawing with Cinzel (`drawFeatures.ts`; names and markers are sized by `textScale`: they follow the map's scale when zooming out but grow only slowly, to at most 1.8 times, when zoomed in, times the sidebar's Label size setting),.
- Claude Code first-run setup: Claude Code isn't bundled and every user signs in themselves. The panel shows `ClaudeInstallSteps` (`ClaudeButton.tsx`) with an install button; `main.cjs` `startInstall` runs Anthropic's official installer (command fixed in `installCommand`, never taken from the page) visibly in the pty and reports `dd:claude-installed`; `claudeCheck` gives installed/version for Settings. The smoke test swaps in a harmless stand-in under `SMOKE`. The terminal panel runs `settings.terminalCommand`: empty means Claude Code with `--mcp-config` and the Assist hooks, anything else runs through the shell in the Claude workspace (which also holds `AGENTS.md` and `GEMINI.md`, harmless next to `CLAUDE.md`: Claude Code reads only `CLAUDE.md` when both exist). Which assistant a start command runs is worked out from the command (`profileFor` in `apps/desktop/assistants.cjs`: claude, codex, gemini, opencode or muse (Meta's Muse Code), also through `ollama launch <x>`; empty is the default, anything else is unknown; Antigravity (`agy`) is no longer connected because Google's terms forbid its use with other products, and the file earlier versions wrote for it, `.agents/mcp_config.json`, which held the key, is only ever cleaned of our entry: `RETIRED_TARGETS`), and `syncAssistantConfigs` writes that assistant's own project file in the workspace so the map tools are connected with no copying: `.mcp.json` (Claude Code started by another program, plus the `enabledMcpjsonServers` pre-approval in `.claude/settings.json`; Muse Code reads the same file once the folder is trusted, so that target's `users` are both), `.codex/config.toml` (a marked block; Codex only reads it once the folder is trusted), `.gemini/settings.json`, `opencode.json`. Our entry is taken out of every other assistant's file (recognised by its 127.0.0.1 `/mcp` address), what else the person put in those files stays, and an invalid file is left alone; the default Claude Code gets the map tools from `--mcp-config` alone, so a second definition can't ask for approval. Settings shows whether the chosen assistant is connected automatically (`describe`). Adding an assistant: its entry in `JSON_TARGETS` (or a writer like `syncCodex`, or a name in an existing target's `users` when it reads that file), a name in `BY_PROGRAM`, tests like `apps/desktop/test/assistants.test.mjs`, a row in `docs/SETUP-WINDOWS.md` §6b (both tables: what Dragon Drop sets up, and what it needs), its choice and "What it needs" line in `ASSISTANT_PRESETS` (`apps/editor/src/assistantPresets.ts`: free, the company's app plan, or paid separately, checked on the company's own pages and dated; a test keeps that list and `ASSISTANTS` the same), and a check against the real tool (its own "list MCP servers" command, with the key only in the environment). The Settings preset dropdown fills the command and shows what the chosen assistant needs (its sign-in and what it costs).
- Battlemap levels (`packages/core/src/levels.ts`, design in `docs/FOUNDRY.md`): a level is a floor document of its own. Level 1 is the project's own files (so a one-level map is stored exactly as before and has no `levels.json`); further levels are in `levels/<id>/` with the same layout (a level's name and links (`copiedFrom`, `origin`, `parent`) are taken from the project's own `project.json` when it loads, `loadLevel`, since a level's files can hold older ones), listed with names and elevations (feet) in `levels.json` (`ProjectStore.readLevels` / `loadLevel` / `saveLevel` / `removeLevelFiles`; an unreadable list is set aside, never overwritten). The hub holds one `MapSession` per level (`OpenProject.runtime`) and `OpenProject.session` is the active one, so every tool, selection and undo works on it unchanged; only the active level's events reach the editors (`wire`), a switch commits any open transaction and re-sends the project (`setActiveLevel`), autosave writes the levels that changed, checkpoints hold every level (and restore recreates removed ones), and `removeLevel` saves a checkpoint first. Messages: `level_set` / `level_add` / `level_update` / `level_remove` and `levels`. Exports: the Foundry scene has a level per level with its own picture (`toFoundryLevelsScene`), the picture, Universal VTT and one-level files are of the active level (named with it). The editor's `LevelBar.tsx` and `Battle.tsx` show the level below faintly: the floor's void is transparent in the editor (`clearVoid`) and the server renders the level below (`Hub.levelPicture`). World maps have no levels (`levels` is null). Stairs, ladders and holes between levels are `MapConnector`s in a level's features (`connectors`; `to` up or down means the next level above or below by elevation; a hole always leads down): the editor's Stairs/Ladder/Hole tools place them, the shared wall layer paints them (`paintConnectors` in `battleLook.ts`, so the editor, previews and exports agree), `toFoundryLevelsScene` writes stairs and ladders as Change Level regions and a level's holes as gaps in a floor region made from its floor (`floorRects`), and connectors that lead nowhere are reported in the export's README (`foundryConnectorProblems`). Claude's tools for them are in `packages/tools/src/levelTools.ts` (`list_levels`, `add_level`, `set_active_level`, `update_level`, `add_connector`, `update_connector`, `remove_connectors`, `list_connectors`; no tool removes a level: that is the DM's), reaching the hub through `ToolContext.levels`; every other battlemap tool works on the active level, and `export_battlemap` / the Export dialog take a `level` for the picture and the Universal VTT file. Roofs are `MapRoof`s in a level's features (`roofs`; a polygon with a look, or an asset-pack picture tiled across it): `renderRoofLayer` (`battleRoof.ts`) draws them as one see-through layer, the editor shows them faintly (`roofView`), previews leave them out unless asked, and the Foundry export draws each roof on its own into a picture cropped to it (`renderRoofPicture`, `battleRoofRects`; RGBA through `encodePngRgba`: `encodePng` drops alpha) and writes it as a **Tile** at the level's top (Surface occlusion, written as both `mode: 2` and `modes: [2]`, placed by its centre) with a **Define Surface ceiling region** over the roof's outline (`toFoundryLevelsScene`), because a level's foreground never fades but a Surface tile does: it is cut to the region's shape while a controlled token is under it (RT8, `docs/FOUNDRY.md`); Claude has `add_roof`, `update_roof`, `remove_roofs`, `list_roofs` (`roofTools.ts`). **Foundry scenes must carry `_stats.coreVersion` (`FOUNDRY_CORE_VERSION`, `foundryScene.ts`)**: without it Foundry v14 runs its old-data migration and replaces the levels with an empty one, and with a value older than the running build it still migrates, so write old AND new field forms where a migration rebuilds one from the other (a tile's `occlusion.mode` + `modes`) and read Foundry's export as the migrated form, not as what to write (found in a real Foundry, build 367; results and the facts they pin down are in `docs/foundry-test-kit/results/v14.367/`, summarised in `docs/FOUNDRY.md`). `apps/server/test/foundryTested.test.ts` keeps the one-level export equal to the file that was tried; if you change what the scene writes, try it in a real Foundry again (`pnpm foundry-kit`) rather than editing that fixture.
- Water (`hydrology.ts`, `hydroSummary.ts`): rivers come from flow accumulation weighted by runoff (`runoffOf(temp, moist)`, so rain decides where rivers start and how big they are), the threshold is a share of the map's total runoff (with `ClimateParams.riversFollowRain`, on for new maps and detail maps, also at least what ordinarily rainy ground would give, `RAINY_RUNOFF`, so a dry map isn't filled with rivers; `noRainRivers` leaves only the rivers of sources and drawn rivers), a lake's outflow is a river head, and `RiverSource`s (`features.sources`, sizes in `RIVER_SIZE_SHARE`) inject extra flow at a point or at a place. `resolveRiverSources` turns them into `inflows` for `computeDerived` (the hub recomputes when they or their place move). `Derived.hydro` is the account that `check_hydrology` reads (`shapes`: every lake with a simplified shore). **Named rivers and lakes** (`waterNames.ts`): a name is `features.waterNames` (`WaterName`: kind, name and a spot in map px; canon, the DM's), pinned to a spot because the rivers stay derived: `riverNet` joins the traced pieces (each `RiverPath` says why its tracing stopped, `end`; where one ends on another, the bigger above the junction carries on: `takeovers`), `riverOwner` gives the river (its head piece) at a point, `riverCourse` follows it to the sea, a lake or a bigger river, `resolveWaterNames` gives each name its water and a label (a smoothed stretch of its river reading left to right, or the lake's middle). The hub sends the `water` message (labels, each name's water, and to editors every lake's shore) after each derive and when a name changes (`Hub.waterView`); the editor draws the labels with the features (`withWaterLabels`, also the export), the Rivers tool (`river`, key `I`, `waterUi.ts`, `WaterPanel.tsx`) opens on **Add a river** (a drag draws a river, a click starts one: a source; sources show as blue dots) and has **Name and select**, which lights up what is under the pointer and names or selects it (`SelectedFeatureKind` "water"). **Drawn rivers** (core `riverDraw.ts`, `riverChannel`; `Hub.drawRiver`, messages `draw_river` / `river_drawn`, Claude's `draw_river`): the line becomes a channel cut into the land, its bed always falling and below the lowest ground beside it (so it holds across a slope), plus a source at its upper end, as one `patch_heights` edit (a box of heights with a features patch: one undo step for both); a line from the coast inland is turned round, one with both ends at the sea is refused (a river can't begin at the coast), and the Map panel's Rivers and lakes section lists the names. **Carving** (`carve.ts`, `Hub.carveValleys` on the compute thread, `carve_valleys` message and tool): valleys along the rivers, floodplains, deltas; land never raised (but deltas) nor cut below the sea; a checkpoint first, one `patch_heights` edit of the box that changed. It can be held to part of the map (`Hub.carvePart`): the whole map, the selection (`where: "selection"`: an area or climate region through `CarveOptions.within`, a soft edge inside it; or the selected river, a named one or a source's, through `courseRivers` and `riverHeadAt`), or one named river (Claude's `river`); the Carve valleys box's Where offers the selection first when there is one. **Lowland rivers** (`ClimateParams.lowlandRivers`, off when missing so existing maps keep their rivers): wide loops on flat ground, oxbow lakes (`Hydrology.oxbows`, painted as lakes through `Derived.lakes` but not in the account), estuaries. Claude: `name_water`, `list_waters`, `remove_water_name`, `carve_valleys`, `set_climate` `lowland_rivers`. **New maps are drained** (`terrainDrain.ts`, run at the end of `generateTerrain`): the generator's ridged mountains leave deep closed hollows, so every hollow deeper than a lake gets an outlet cut (or is raised into a shallow bowl), keeping a few as lakes by `GenerateTerrainParams.lakes` (none, few (default), some, many = as before); existing maps are never changed.
- Selection (`packages/core/src/selection.ts`): `Selection` is a point, an area (rect/circle/polygon) or a feature id; the editor sends it (`{t:"selection"}`, with `lock`, and `{t:"view"}` for what is on screen), the hub keeps it per open map (reset on open; a deleted feature deselects) and echoes it, and Claude reads it with `get_selection` (`selectionReport`). The lock is `MapSession.editLock` (set by the hub from an area or a climate region): in `execute()` it applies to author `claude` only, clips height changes with a feathered mask (nothing outside the shape changes, the undo rect shrinks to the shape), and throws `LockedEditError` for feature edits outside the shape and for sea level, climate settings and checkpoint restores. The editor's side is the Select area tool in `MapView.tsx` (rectangle, circle and freehand are drags; polygon is corner by corner with `polyDraft`, closed by double-click, Enter or a click on the first corner), `SelectionBar.tsx` (lock checkbox, "Ask Claude about this" box that types one line into the terminal through `useAssist().ask` only when Claude Code is idle, `askMessage` in `assist.ts`), and `store.setSelection`.
- Rivers in the painted style are painted into the map by `renderPainted` (`riverPaint.ts`), not drawn over it: `rasterRivers` gives each pixel near a river its distance to the water's edge, the river's size and how steeply it drops (m per km); the painter then shades the water from the ground (calm dark water on the flats, rapids and falls where it drops, canopy hiding narrow rivers in jungle, brackish at the mouth), paints banks that follow the land (floodplain, gravel, oasis ribbon, mud), and the shading sees a valley cut into the ground (`valleyDepth`). The paint worker gets the rivers with every climate frame, `derivedChange` counts a changed river as a change, and the Rivers layer switch is `PaintView.rivers`. The vector overlay in `MapView` (and the export's rivers option, and previews from the server) are for the Relief style only. In `hydrology.ts` a river's meander follows its slope (straight when steep, wandering on the flat) and dies away at junctions so tributaries meet exactly.
- Biomes in the painted style (`biomeLook.ts`): land that is neither jungle nor desert gets the ground its climate makes, from `biomeWeights(t, m, e, rugged)`: tundra, boreal conifer, temperate mixed forest, warm broadleaf forest (the temperature bands add up to one and fade into each other; above the treeline, about 700 m, the forest's share becomes alpine meadow), steppe or savanna where it is drier, marsh on low flat wet ground and along big rivers (the painter passes the river raster's closeness to `biomeWeights` as `nearWater`). A wet archipelago has moisture near 1 almost everywhere, so the variety comes mostly from temperature (latitude and height). `paintBiomes` mixes each biome's texture (from the canopy, clump, hue, rock and fine noise) over the palette colour, scaled by `(1 - jungle) * (1 - desert)`; tall forests also hide gentle low rock. On top of the biomes lies more ground in particular places (`Ground` in `biomeLook.ts`): beach on low gentle coast, mangrove on warm wet coast (further in along a river), reeds and lake-shore wetland (`lakeShoreDistance` gives the distance to a lake), glacier on the highest coldest snowy ground (painted after the snow), heather moor and peat bog on cool wet uplands, Mediterranean scrub (chaparral) where it is warm and not quite dry, badlands where dry ground is rugged, salt flats on very dry low flats, stony desert (the desert's version where the ground is rugged), and the wet forests: cool temperate rainforest on a wet coast below the treeline, cloud forest on warm wet mountainsides, bamboo stands and autumn colour in the cooler mixed woods (the last three are patchy: the painter breaks them up with noise). `get_selection` reports the shares of each kind of ground in an area (`biomes`, including jungle and desert) and the most common as `climate.biome`.
- Volcanic ground is a climate-region setting like bare stone: `ClimateRegion.volcanic` (0..1) gives a `Derived.volcanic` plane (`regionVolcanic`), which travels after the stone plane on the wire (`packDerived`: the stone plane is zero-filled when only volcanic is there), counts in `derivedChange`, and is painted by `renderPainted` as pale ash plains with cinder-brown patches and near-black basalt fields. Lava flows (`lava.ts`) are worked out like rivers but with a lava's physics, from the heights and the volcanic plane only (so every tile agrees; `lavaOf` caches them per `Derived`): vents at the summits and upper flanks of volcanic ground; each flow has a heat budget that every step spends (cheap on steep flanks, dear on flat ground where lava stalls); depression filling like the rivers (`computeFlow` on the volcanic part of the map: a flow fills a small hollow and spills over, but a basin deeper than 90 m holds it); forks that don't merge; narrow at the vent and broad lobes with a blunt front; meander; it ends where the volcanic ground ends or at the sea. About a third of flows are fresh and glow (scorched edge, dark crust over an orange body, bright core, self-lit and painted after the shading and the rivers, which they bury); the rest are cooled black basalt with ropy streaks. `rasterLava` gives each pixel its distance to the nearest flow. River banks leave volcanic ground alone, like stone. Claude sets it with `volcanic` on `add_climate_region` / `update_climate_region`, only where the DM said the land is volcanic; the editor's region panel has a "Volcanic ground" tick.
- Place kinds (`packages/core/src/placeKinds.ts`) are the one list of what a place can be (`PLACE_KINDS`: id, name, group, label size, name-placement rank, hint, and `picture`): `PlaceType`, `PLACE_SIZE`, the zod enum of `add_place` / `update_place`, the editor's picker (`PlaceKindPicker.tsx`, grouped, in the Place tool and the inspector) and the name-placement order all derive from it. The first nine kinds are the original abstract symbols (drawn by `marker()` in `drawFeatures.ts`, kept as they were so old maps look the same); every other kind is a small vector picture in `placeIcons.ts` (shapes in a -1..1 box: ink with a white outline, some white cut-outs and tints; written against a tiny `IconCtx` so it also runs in tests). `drawPlaceMarker` draws either kind. Adding a kind: add it to `PLACE_KINDS` and, if `picture` is true, to `PLACE_ICONS` (a test fails until both agree). Unknown kinds from a newer file read as "other" (`placeKind`). The server's raster previews still draw a plain dot for every marker.
- `GROUND_INFO` in `biomeLook.ts` is the one list of every kind of ground (id, name, group, swatch colour, where it appears, `recipe` = how to get it); it also feeds the `list_grounds` tool and the "Ground types" section of `MAPMAKER_INSTRUCTIONS`, so Claude Code in the terminal knows the grounds (a new ground needs its recipe, and the instructions' list updated); the editor's "Ground legend" panel (`GroundLegend` in `Panels.tsx`, painted style only) shows it, and a test keeps it in step with the biomes, the extra grounds and the region-set ones.
- **Files held by another program** (OneDrive syncing Documents, a virus scanner): Windows refuses to replace a file while it is open elsewhere. `atomicWrite` (store.ts) writes a temporary file of its own name and renames it over, waiting out a hold for about 10 s (`REPLACE_WAITS_MS`) and removing its temporary file if it gives up; the hub writes a map's saves one after another (`OpenProject.saving`) and tries a failed save again by itself (`saveFailures`: 2 s, then doubling to a minute). Tried with a real hold (a Python script holding the file open) on a 2048 map; `saveRetry.test.ts` checks the retry. `pnpm e2e` can play a slow PC: `E2E_CORES=2` (this process, the server and the browser on two cores, Windows) and `E2E_CPU_SLOWDOWN=4` (the page). The workflow's `older-windows` job installs the built installer on `windows-2022` and runs the installed app's start-up check.
- Keep the server's main thread free: never use the synchronous gzip/gunzip (a 2048 map is 17 MB and froze it for about 500 ms per save), take any snapshot of the map before the first `await`, and keep heavy maths in the compute workers. In the editor, a full-map repaint is expensive (about 1.5 s of main thread): derived layers repaint only the box that changed (`derivedChange`), and the load placeholder is `renderPlaceholder`.
- Painting runs in a worker, never on the main thread: `PaintEngine` (core) holds heights, climate layers and noise and makes tiles and sliced full repaints (blurs computed once, `paintPrep`); `paintWorker.ts` / `paintClient.ts` wrap it; the map view only draws the pixels it is sent. Don't hold or upload big buffers on the main thread (an 80 MB `fetch` body blocked it for seconds): fetch and upload in workers. The texture noise is cached on disk (`noiseFile.ts`, `NoiseStore`, `/api/noise`): if you change what `noise.ts` or `noisecache.ts` produce, bump `NOISE_CACHE_VERSION` (a fingerprint test fails until you do).
- Assist mode: `packages/core/src/assist.ts` (pure rules and the typed message, tested), `POST /api/claude-hook` in `apps/server/src/http.ts` (Claude Code's hooks report idle/busy/blocked; the answer must stay empty because hook output can reach Claude), the desktop app writes the hooks into its Claude workspace `.claude/settings.json` (`withDragonDropHooks` in `main.cjs`, keeps the DM's own settings) and `dd:term-status`, the editor side is `useAssist.ts` and `assistBus.ts`. Claude Code sends no Stop when it is interrupted, so after an Esc typed into the terminal the desktop app watches its screen and, once it no longer looks busy and has been quiet 2 s, posts an `Interrupted` event (`watchInterrupt` in `main.cjs`; `claudeStateAfter` makes a busy or asking Claude idle; it changes nothing otherwise). The desktop app also posts a SessionEnd to `/api/claude-hook` whenever any terminal program ends, so a stale idle state can't outlive Claude and Assist never types into another program. Never type into the terminal unless the hooks say Claude is idle: an Enter at a permission prompt would answer it. Typed text must be one line with no control characters (`oneLine`).
- Reference pictures (core `pictures.ts`, the editor's `References.tsx`): the DM adds them with the References panel's Add picture button, by dropping a picture anywhere in the window (App's window `drop` listener; the chat panel handles its own drop first, and App skips an event it already took) or by pasting one on the map, besides the API chat's attachments. What a file is comes from its first bytes (`pictureKind`), and `referencePictureProblem` gives the note for one that can't be used (HEIC, GIF, SVG, PDF, too big): the editor checks before sending and the server again (`ProjectStore.addRef` throws `PictureRefused`). Uploads go from a worker (`pictureUploadWorker.ts`) as the raw file to `POST /api/projects/<id>/refs` (`x-file-name` header; 415 or 413 with the message); `ref_rename` / `ref_remove` rename one (its type stays) or move it to `backups/removed-pictures`. Ctrl+V on a map pastes whichever was copied last, map items or a picture: Ctrl+C on map items also writes `MAP_ITEMS_CLIPBOARD_TEXT` to the system clipboard through the copy event, and the paste event decides (`pasteChoice`; `clipboard.ts`). "Ask Claude…" on a picture types `pictureAskMessage` into Claude Code under the same idle rules as the selection bar.
- City maps (**called settlement maps in everything the person reads**: a village, town or city; code, files, test ids and Claude's tool names keep `city`; core `city.ts`, `cityRender.ts`; the editor's `CityView.tsx`, `CityPanels.tsx`, `cityUi.ts`; Claude's `cityTools.ts`; plan and stages in `docs/CITY-MAPS.md`): a third kind of map, `meta.kind === "city"`, in METRES from the top-left corner. It is its own small document, not a stretched battlemap (a battlemap assumes at most 150 squares a side, 20+ px a square and a textured floor cell: a city is 1 to 6 km). `meta.city` (`CitySpec`: `widthM`, `heightM`, `cellM`) sizes it; the heightfield holds the ground material of coarse `cellM` cells (the battlemap's `MATERIALS` ids, painted with `paint_floor` in cell units, grass to start); `features.buildings` (`MapBuilding`: an outline in metres, a roof look, colour, flat, kind, name, floors) and `features.streets` (`MapStreet`: points and a width) are set with the patch operations `upsertBuildings` / `removeBuildings` / `upsertStreets` / `removeStreets`. - **Starting up never fails because of a map** (`Hub.ensureProject`): the map open last time, else the first that opens; one that won't (saved by a newer Dragon Drop, unreadable) is skipped and left as it is, and the first editor to connect is told (`startupNotes`); with nothing openable a new First Map is made beside them. Before 0.1.11 a newer-format city stopped the program at start, so it couldn't even reach its updater.
- Map files are versioned (`packages/core/src/format.ts`, `formatVersion` in `project.json`; a missing one means 1). If you change what a saved map contains or means (a field renamed, a unit changed, a layer stored differently), raise `CURRENT_FORMAT` and add the step to `MIGRATIONS`, with a test; adding an optional field old files simply lack needs no new version. `ProjectStore.load` refuses a newer map (`NewerFormatError`, files untouched), copies an older one to `backups/` before migrating it, and sets an unreadable `features.json` aside instead of overwriting it (`takeNotices` hands the hub what to tell the person). Rolling backups are checkpoints with `auto: true` (`Hub.maybeAutoBackup` after a save, `HubOptions.autoBackupMs` / `autoBackupKeep`, `MAPMAKER_AUTO_BACKUP_MINUTES` / `_KEEP`; `pruneAutoCheckpoints` never deletes a person's own). Checkpoint writes for one map run one after the other (`serial`), and a checkpoint snapshots the map before its first `await`. `docs/MAP-FILES.md` describes the files for users.
- Asset library (`apps/server/src/assets.ts` and `zip.ts`; `packages/core/src/assets.ts`, `pck.ts`, `imageSize.ts`): the folder set in Settings (`MAPMAKER_ASSETS_DIR`) can hold any mix of folders of pictures (each folder directly inside it is a pack; what kind each picture is comes from its path, `categoryOf` in core `assetKinds.ts`: a pack file's own `textures/<kind>/` layout first (also under `packs/<id>/`), then the words in its folder names, deepest first, then its file name, weighed per kind (`WORDS`), and a pack's thumbnails, cover picture and a Mac's `._` copies are data, never offered; worked out once per picture when a pack is read (`Entry.cat`); a picture whose path says nothing takes its pack's own name's kind (`kindOfPackName`), and one still unknown is looked at after the scan, one at a time on the worker (compute op `look`, core `pictureKindHint` in `pictureKind.ts`: an empty border is an object, an about-square picture with nothing empty that runs on round its edges is a floor), remembered in the cache folder's `picture-kinds.json` (raise `PICTURE_KINDS_VERSION` when the judging changes). **No asset packs from other makers ship with Dragon Drop**: every buyer's library is laid out their own way, so test on made-up libraries of several layouts, never only the person's. The one exception is Dragon Drop's own **Starter Pack** (`apps/server/starter/Dragon Drop Starter Pack`: ten CC0 floor textures from Poly Haven, Gravel and Forest Floor retuned so their swatches read right, and twelve objects of our own in `Objects/`, drawn by `tools/starter-objects/draw_objects.py` (CC0; rerun it after changing it), all listed in its `CREDITS.txt`, which `starterPack.test.ts` keeps in step with the pictures; a new picture there must be CC0 or the like, looked at, and credited): `Config.starterDir` (`MAPMAKER_STARTER_DIR`, empty for none, as `pnpm e2e` runs; else the repository's copy; the Windows app carries it in `resources/starter` and always passes it), read as one more folder pack, first, with or without an asset folder (`AssetLibrary(dir | null, cache, starterDir)`, `PackInfo.builtIn`), so its ids stay `dragon-drop-starter-pack:Floors/...` whatever the folder holds; the status says `ownFolder` and `starter`, and with only the Starter Pack the pickers and the Assets tab say how to add your own packs), `.zip` files (`readZipIndex`: stored and deflated, zip64, inflate limited to the declared size, unsafe paths dropped) and pack files made by other map tools (Godot PCK archives: found by a name ending `_pack` or `.pck`, then checked by the `GDPC` signature). Everything is read in place and never copied. Pictures are PNG, JPEG or WebP: `decodeImage` (`packages/tools/src/images.ts`) decodes all three, WebP through libwebp 1.6.0 compiled to WebAssembly (`webp.ts`; the module is carried in `webpWasm.ts`, generated by `tools/webp-wasm/build.sh`, which says how to rebuild it and moves to a newer libwebp; it has no imports, each picture is decoded in a fresh instance, an animated WebP is skipped as missing, and `webp.test.ts` pins the checksum, the library version and the fixtures to byte-exact libwebp output). Reference pictures (the chat's attachments, sketch import) accept the same three. A pack's own info file (`packs/<id>.json` or `pack.json`) may say `allow_3rd_party_mapping_software: false`: that pack is listed but never served or drawn, and that must stay. Don't name other mapping programs or their file formats in code, UI text, docs or tests (say "asset packs"); test fixtures use made-up extensions such as `.example_pack`. Objects are 256 px per grid square at scale 1. **Battlemap walls** are built of a look (`MapWall.look`: stone, the default, brick, wood, plaster, rock) or a pack picture (`MapWall.asset`, `tile`): `renderWallLayer` (`battleLook.ts`) draws either (`lookColour`, `samplePicture`: a strip with width over height 2.5 or more is laid along the wall, anything squarer tiled along it) from `pictureFor`, which the editor fills from the picture (`wallPictureFor` in `Battle.tsx`) and the server from `AssetLibrary.wallPicture` (`Hub.battleAssets` `wallPictures`, the compute job's `wallPictures`); a door or window can have its own picture too (`MapWall.portal`, drawn in the opening by `paintPortal`, kept apart from `asset` so a window's frame keeps its wall's material; the Door and Window tools' pickers, `PortalPicker`); a wall with no look or picture is stored and drawn exactly as walls always were (`wallStyleOf` writes only what is set), and `roomWalls`, `insertDoor` and walls around the floor keep or take the style. The pack part of the floor and wall pickers is one component (`PackGrid.tsx`; its `testId` names the picker and `item` each swatch: give them different values, or a test counting the swatches counts the picker too). **Battlemap paths** (`features.paths`, `MapPath`: roads, tracks, streams; patch `upsertPaths` / `removePaths`; `featureOps` knows them as kind `path`) are drawn by `renderPathLayer` (`battlePaths.ts`: `smoothPath` rounds the corners, a look from `PATH_BASE` or a pack picture laid along it, soft edges) over the floor and under everything else, in `renderBattle` and in the editor's own path layer (`buildPaths`); their pack pictures travel with the walls' (`wallPictures`). The editor's Path tool is `Y`; Claude has `add_path`, `update_path`, `list_paths`, `remove_paths` (`pathTools.ts`). A light can take its shape from a pack light picture (`MapLight.glow`: `drawBattleLights` uses its brightness, tinted, instead of the round fall-off; the editor tints it in `glowCanvasFor`; Claude's `glow` and `update_light`). Every Assets tab kind is usable: patterns as floor textures, roofs as the Roof tool's picture (`BattleUi.roofAsset`), lights as a light's shape. The person's notes on pictures (`AssetLibrary.loadNotes`: favourites, the 48 used last, and words for pictures from the person or Claude's `tag_assets`) live in the cache folder's `asset-notes.json`, are searched with the names (`list` `only`, `tagsByPack`), and reach the editor through `POST /api/assets/favourite`, `used` and `tags`; every pack picker (`PackGrid`) and the Assets tab have ★ Starred and Recent and star on right-click. Battlemaps Dragon Drop makes (`Hub.createBattleFromWorld`, `createBattleFromCity`) are dressed with fitting pack pictures by `dressBattleWithPacks` (`apps/server/src/battlePack.ts`: floors by `FLOOR_WORDS`, walls, doors, windows; starred first; `packPictures: false` on the messages and Claude's `pack_pictures` keeps the built-in looks). Its own choice passes over what a DM wouldn't take (`suitsFloor`, from the 48 px thumbnail as a floor shows it: a floor is painted from a picture's colours, see-through parts too): grey pictures for ground with a colour (`COLOURED`; packs hold grey "colour it yourself" copies), water that isn't bluish, overlays, masks and decals (`OVERLAY`), flat colours and near-black ones, and a wall's end, corner and post pieces (`PIECE`). Two versions of one pack (the same pack id, names that differ by their version) are one: the newest is offered, the older kept under its own key, and a picture asked for from a version that is gone is looked for in the newest (`newerVersionOf`, `baseKey`). A wall or path picture is laid along its line when it is long or its top and bottom edges are see-through (`laidAlong` in `battleLook.ts`), else tiled like a floor. The battlemap's floor picker lists every pack floor texture (`PackFloors.tsx`, searched through `/api/assets/list?cat=terrain`); a chosen one joins the map's palette through `floorTextureFor` (`floorTextures.ts`, shared with the Assets tab; at most `MAX_FLOOR_TEXTURES`).
- File types (`packages/core/src/formats.ts`, `docs/FORMATS.md`): the one list of what Dragon Drop reads and writes, with what does not work. The chat's file picker (`REFERENCE_PICTURE_ACCEPT`), the reference listing, the asset library's picture, zip and pack-file rules and the battlemap export formats (`BATTLE_EXPORT_FORMATS`: the export tool, the download route and `Hub.battleExport`) all take their lists from it, and `docs/FORMATS.md` is made from it with `pnpm formats`; a test fails if the page and the list differ or if a claim stops being true (what decodes, what the library lists, what exports).
